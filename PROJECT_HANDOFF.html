How the system works

1. Flutter Android app

mobile_app/lib/main.dart contains most mobile screens, navigation, state, and API calls. The API address is compiled into the build as API_BASE_URL. The app uses secure storage for the signed-in session.

2. Express API

server.js is the trusted service. It checks sessions and roles, applies library rules, reads/writes SQLite, and talks to Firebase Admin when configured. Mobile and dashboard requests go to /api.

3. SQLite

The local aclc_library.sqlite file holds operational library records such as books, copies, reservations, loans, returns, gate events, and audit history. Production needs durable persistent storage and backups.

4. Firebase Auth and Firestore

Firebase Authentication is the account identity provider. Firestore stores a synchronized user profile at users/{uid}. A server-only Firebase Admin credential links/synchronizes users; the Android JSON is public client configuration, not an API server address or admin key.

5. React administrator dashboard

web-dashboard/src/App.jsx contains dashboard screens and workflows. It calls the same Express API; it does not bypass server authorization or write directly to SQLite.

6. Email, gate, and LIRA

Gmail SMTP sends verification/approval/reset messages. Gate endpoints issue short-lived authorization nonces and expect an authenticated device. lira-ai.js handles optional AI responses with a server-side key and safe local fallbacks.

Account flow

A student or teacher registers, verifies email with a six-digit code, then waits in the administrator approval queue. Approval activates the account and its library ID/QR. Firebase Auth, Firestore, and SQLite identity records are intended to stay linked. Pending or rejected accounts must not borrow books or use entrance features. Public users cannot grant themselves staff or administrator roles.

Library flow

Book search, inventory, reservations, checkouts, returns, penalties, payments, notifications, reports, QR credentials, and access logs are handled by API routes and stored operationally in SQLite. The backend, not only the UI, must enforce borrowing limits and role permissions.

Important file map

server.js

Express app, API routes, SQLite setup/migrations, auth and role checks, Firebase/email integration, admin bootstrap, and API startup. In test mode it skips loading local .env secrets.

lib/firebase-account-reconcile.js and scripts/link-existing-firebase-accounts.js

Safe legacy account reconciliation. It defaults to dry-run, requires a fresh Firebase Admin credential path outside the repository to apply, matches verified emails exactly, refuses role mismatches and UID conflicts, and links Firebase Auth UID, Firestore profile, and SQLite.

migrations/001_initial.sql through 007_book_cover_url.sql

Ordered SQLite schema changes. Do not edit production schema casually; back up data and add a new migration for future schema changes.

lira-ai.js

Optional LIRA provider integration and local fallback behavior. Provider credentials belong on the server only.

test/

run-api-tests.js launches tests against an isolated temporary database; API, circulation/gate, LIRA, and Firebase account reconciliation tests live beside it. Tests skip local .env to avoid touching live services.

mobile_app/lib/main.dart

Main Flutter UI and mobile workflows. The mobile project also has pubspec.yaml/pubspec.lock, image assets, Android Gradle config, manifest, and Kotlin MainActivity.kt.

mobile_app/android/app/google-services.json

Firebase Android client setup for the ACLC Firebase project and Android package. It is not secret, but must match the Firebase app/package registration.

web-dashboard/src/App.jsx

React dashboard pages and actions. main.jsx starts React; App.css and index.css define dashboard styling.

package.json and lockfile

Backend dependencies and commands. npm start starts the API; npm test runs automated backend tests. The dashboard has its own package files.

.env and .env.example

.env contains local secrets and is ignored by Git. .env.example documents variable names and safe placeholders. Never paste or commit the real file.

render.yaml

Render deployment blueprint for the Express service, persistent SQLite disk, health path, and production environment variable names. A blueprint does not mean a live service exists.

System documents

README.md, SYSTEM_ARCHITECTURE.md, API_DOCUMENTATION.md, DATABASE_DESIGN.md, HARDWARE_INTEGRATION.md, TESTING_PLAN.md, and DEVELOPMENT_PLAN.md explain setup, data, APIs, hardware limits, tests, and roadmap.

Secrets and generated files

mobile_app/android/key.properties, keystore files, local SQLite databases, build output, and node modules are local/generated/private data. Keep them out of shared prompts and source control.
